# Stage 7: Page design and the handoff kit

**Purpose:** define what each page type contains and how it should look, then hand the
developer and designer everything they need: CMS requirements, page anatomy, briefs and
reference pages.

The person following this playbook usually does not code or design. Their job here is to
**decide and brief well**. A clear brief with references is the difference between a
template that works and three rounds of rework.

---

## Step 7.1: Write the page anatomy for each page type

**What it means:** a plain-text wireframe listing each section in order, what goes in it,
and whether it is unique to the page or shared across the page type.

**How to do it:** start from the matching entry in `library/page-types.md` and adapt it.
For every section, mark:

- **Unique:** comes from the row in the content sheet (must differ meaningfully per page)
- **Shared:** the same on every page of this type (CTA, trust logos, process overview)
- **Auto:** generated by the CMS (breadcrumb, related pages, schema)

**Rule of thumb:** a reader skimming two pages of the same type should see different
content in most of the screen, not the same blocks with a word swapped. If shared blocks
take up most of the page, cut or shorten them.

**Variation rules so pages do not look mass-produced**
- Different page types get different layouts, not one layout with different text.
- Within a page type, allow optional sections (a table, a comparison, a timeline, a
  case-study block) that appear only when the row has material for them.
- Avoid stock boilerplate repeated on every page: long logo strips, the same three
  testimonials, generic "why choose us" lists.

**Worked example (industry solution page)**

```
1. Hero                      Unique   Industry's problem in one line, H1, short intro, CTA
2. Pain points (3 to 5)      Unique   Cards, each a specific problem in this industry
3. How it works here         Unique   Numbered workflow specific to the industry
4. Proof                     Unique   Case study block with one real result figure
5. Before / after            Optional Table, only if the row has the data
6. Engagement or features    Shared   Short, links to the service page
7. FAQs                      Unique   Only questions with substantive answers
8. Related pages             Auto     Sibling industries, the pillar page
9. CTA                       Shared
SEO block (not visible):     meta title, meta description, canonical, schema @graph
```

**Done when:** each page type has an anatomy with every section marked unique, shared,
optional or auto.

## Step 7.2: The SEO block for every page

Keep on-page SEO in a separate block of the content sheet and the page draft, never mixed
into the body copy:

- focus keyword
- meta title (about 50 to 60 characters) and meta description (about 140 to 160)
- slug
- canonical (self-referencing by default)
- breadcrumb parent
- schema: one JSON-LD script per page using a single `@graph`

**Schema example (one script, linked pieces)**

```json
{
  "@context": "https://schema.org",
  "@graph": [
    {"@type": "Organization", "@id": "https://example.com/#org", "name": "Example Co", "url": "https://example.com/"},
    {"@type": "WebPage", "@id": "https://example.com/solutions/healthcare/#webpage",
     "url": "https://example.com/solutions/healthcare/", "name": "Data analytics for healthcare",
     "isPartOf": {"@id": "https://example.com/#website"},
     "breadcrumb": {"@id": "https://example.com/solutions/healthcare/#breadcrumb"},
     "publisher": {"@id": "https://example.com/#org"}},
    {"@type": "WebSite", "@id": "https://example.com/#website", "url": "https://example.com/", "name": "Example Co"},
    {"@type": "BreadcrumbList", "@id": "https://example.com/solutions/healthcare/#breadcrumb",
     "itemListElement": [
       {"@type": "ListItem", "position": 1, "name": "Home", "item": "https://example.com/"},
       {"@type": "ListItem", "position": 2, "name": "Solutions", "item": "https://example.com/solutions/"},
       {"@type": "ListItem", "position": 3, "name": "Data analytics for healthcare"}
     ]},
    {"@type": "FAQPage", "@id": "https://example.com/solutions/healthcare/#faq", "mainEntity": []}
  ]
}
```

The developer generates this from CMS fields. Only include FAQPage when the page shows FAQs.

## Step 7.3: Check the CMS can do what the pages need

**What it means:** before any page is built, confirming the CMS supports the fields and
features the structure depends on.

**How to do it:** go through `templates/cms-requirements.md` with the developer, line by
line. It is written in plain words so a non-technical person can ask "does ours do this?".
The essentials:

- a separate collection (content type) per page type
- control over slug and folder
- editable meta title, description, canonical and robots per page
- a schema output built from fields
- an automatic XML sitemap with real lastmod dates, split by section
- breadcrumbs generated from a parent field
- a related-pages block filled automatically
- bulk import or API publishing from a sheet
- draft and publish status
- flexible sections that can be added, removed or reordered per page
- content present in the page source, not loaded later by the browser
- redirect management

**Done when:** every line is marked "yes", "yes with work" (with an estimate) or "no" (with
a workaround). Anything marked "no" for breadcrumbs, sitemaps or source rendering is
resolved before production starts.

## Step 7.4: Brief the developer and the designer

**How to do it:** fill `templates/developer-brief.md` and `templates/designer-brief.md`,
one per page type. Each brief includes:

- the page anatomy from step 7.1
- the CMS fields and URL pattern (developer) or section treatments (designer)
- two or three reference pages from `library/reference-gallery.md`, with a note on what
  to look at in each
- what "done" looks like

**Tone:** a collaborative request. "Could we set up the industry collection with these
fields?" works better with a team you do not manage than "Build this by Friday."

**Worked example (shortened)**

> **Page type: Industry solution page** (for example "Audit management software for
> healthcare")
>
> **For the developer:** collection `industry-solutions`, URL `/solutions/{industry}/`.
> Fields: industry name, H1, problem summary, 3 to 5 pain points, workflow steps, case study
> (reference to the case studies collection), FAQs, meta title, meta description. Related
> pages: automatic, same parent plus the product page. Breadcrumb: Home › Solutions ›
> {Industry}. Schema: WebPage, BreadcrumbList and FAQPage in one @graph.
>
> **For the designer:** the hero opens with the industry's problem, not the product. Pain
> points as cards, workflow as a numbered visual, case study as a highlighted block with one
> result figure. It must look clearly different from the capability and location page
> types.
>
> **References:** Zapier's app pages for hub-to-child linking; Wise's currency pages for one
> working component per page.

## Step 7.5: Trust, accuracy and speed

- **Who is behind it:** add a short "reviewed by" line (name and role of a subject expert)
  to programmatic pages, and link to an about or team page. It costs little and supports
  the "worth existing" case.
- **Claims check:** in regulated topics (finance, health, compliance, legal), the approver
  signs off claims before scaling. Case studies may be under NDA; check before naming
  clients.
- **Speed:** one slow template means hundreds of slow pages. Ask the developer to check the
  template with PageSpeed Insights before scaling, especially images and scripts.
- **International:** if pages target several countries in one language, discuss hreflang
  with the developer before launch, not after.

---

## Checkpoint for stage 7

Page anatomy per type, SEO block defined, CMS requirements confirmed, developer and
designer briefs sent with references, and a reviewer and claims process agreed.
